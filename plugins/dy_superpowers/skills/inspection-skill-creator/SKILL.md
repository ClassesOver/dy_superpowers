# 创建巡检技能

## 目标与输入

把当前调研模板和源码依据整理成可维护、可验证的领域巡检 skill。输出入口、源码查询参考和验证结果；业务要求读取最新确认答卷及附件，不另建静态巡检矩阵，项目实际结论不进入技能包。

先读取 [编写合同](references/authoring-contract.md) 和 [巡检通用流程](../../references/inspection-workflow.md)。输入为业务模块与触发场景、现有/目标 skill 目录、检查清单与验收依据、源码位置/版本、目标 Odoo 版本及可用工具。实际项目公司、岗位或金额未知时列调研问题，不能填成通用默认值。资料不全时仍可生成明确标注能力限制的草稿。

## 设计和生成

1. 检查目标目录、仓库约定、已有引用与模块支持。已有 skill 优先定点修改；保留原始检查键、标准和历史引用。来源冲突先建映射及差异清单，不能靠改号或删项消除。
2. 以 [入口模板](assets/inspection-skill.template.md) 为骨架，统一为目标与输入、适用范围、执行流程、答卷缺口、源码对照、结果与报告、参考资料。通用执行规则引用共享流程，领域入口保留业务重点和真实能力状态；不复制 Excel 列号、sheet 序号或合并布局到执行规则。
3. 逐子项定义调研问题、适用条件、完整验收标准及证据要求。区分配置只读核验与必须有岗位正反例/边界例的业务效果验证；缺少依据的标准列候选待确认，不能自称企业已批准标准。
4. 依据源码核对技术模块、持久模型、字段与父子关联，为可证明的配置写最小查询配方。每条配方给出范围、最小字段、分页/归档/日期语义和证据限制；源码或范围未核实的配方列为待核实，不编造可执行 domain。具体核查项见编写合同。
5. 写清调研与巡检工具各自的支持状态。当前只有费用/总账接入模板答卷及正式巡检报告。其他领域先核实模板和工具支持，未接入时仅人工核对，不冒称自动门禁/保存支持，不能换成已支持模块名调用工具。若任务还要求接入代码，把接入作为明确的后续开发范围，不因创建目录就声称完成。

## 验证与交付

核查 frontmatter 名称/描述、插件内相对引用、问题标识与模板覆盖。确认目标 skill 所有引用文件存在，模板占位符已替换，正文为中文，入口能路由到通用流程及查询参考。

对新增或修改的确定性代码先写 pytest 回归，验证可观察行为；文档以独立应用场景验收，不写只断言措辞的测试。让独立 agent 在隔离临时目录使用生成的 skill：完成一个正常场景、一个调研/字段缺失场景、一个范围/版本变化场景；新领域另验证工具未接入时的交付说明。不得给评估者预设答案，不连接业务系统或发布结果；发现遗漏再修订重验。

在开发仓库运行相关 pytest、`git diff --check` 和 `bash scripts/validate-plugin.sh`；skill 元数据和安装测试通过只证明包可发现，不证明真实业务验收通过。缺工具、套接字限制、live 未启用等分别报告，不把跳过视为通过。安装后的插件若没有开发仓库，只报告可完成的静态/应用验证及尚缺检查。

交付时列出生成/修改文件、检查键覆盖、源码核对范围、自动工具能力、验证结果及待确认事项。技能可用性、真实账套验证、业务验收分别下结论。创建 skill 不自动导入项目记忆、发布 Wiki 或执行 Odoo 配置变更。
