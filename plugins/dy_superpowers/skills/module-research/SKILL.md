# 模块调研

## 目标

通过多轮问答和核对调研材料，形成按项目、模块、检查项和适用范围组织的可追溯事实。用户要求导入已有调研结果时，任务是完整提取来源中的有效调研结论并按检查键记忆；不能把该要求降为只保存摘要或几个示例。解析完成只表示来源已读取；记忆中的 `confirmed` 表示满足业务确认与写入门槛，可供巡检引用，不表示配置验收通过或巡检通过。

## 调研来源

先按用户文字和附件内容识别模块；图片、截图和扫描件先按[源文件解析与完整性核对](references/source-intake.md)完成最低限度解析，不能先向用户提出通用项目问题。模块无法判定时，唯一允许的前置问题是模块归属；不得先追问项目名称、上线单位或阶段。识别后第一步读取对应模块调研指南和用户提供的源材料：费用模块：读取[费用调研指南](references/expense-research-guide.md)；总账模块：读取[总账调研指南](references/general-ledger-research-guide.md)；其他模块使用其对应调研指南。调研阶段不要读取巡检矩阵；读取指南后直接从指南的问题、提取要素和附件结构中提取公司/院区、业务范围、上线阶段、期间、例外、依据等缺口。优先复用当前会话中用户明确给出的事实和回答，只针对指南要求的缺口追问。巡检矩阵仅在巡检校验或确认结论回链时由对应流程按需读取，不替代模块调研指南中的汇总问题、逐点提取问题或附件字段。仓内统一入口为 `scripts/research_sources.py <来源文件> --module <模块> --workspace <当前项目工作区>`，将完整解析结果写入工作区固定隐藏目录 `.dy_superpowers-parsed/`，终端只返回状态与档案路径。解析档案不是记忆，不进入 Basic Memory 或 Wiki；候选结论仍须按本 skill 的确认、映射和回读流程处理。

模块路由以用户任务及材料业务语义为先，不以旧编号前缀覆盖明确的模块。费用、报销、费用政策、费用项目等业务对应费用，必须先读 `references/expense-research-guide.md`；总账、凭证、制证、期间等业务对应总账，必须先读 `references/general-ledger-research-guide.md`。只有缺少业务语义时才用 `EXP-` 或 `GL-` 辅助判断。总账文件混用旧 `EXP-` 编号时仍走总账指南，编号冲突列为未映射项，不切到费用、不自行改号。未读取对应调研指南前不得开始提问、整理候选结论或写入记忆；模块无法判断时先只询问模块归属，不得用通用问题替代模块 QA。

调研产出的自由主题结论（如"费用政策口径概览"、"两家医院范围差异"）在用户确认后通过 `dy_notes_write` 写为 wiki 记忆页（Basic Memory 兼容 md：frontmatter + `[[双链]]`，位于 `.dy_superpowers/notes/`，自动进入 `dy_memory_search` 索引）；按检查键的调研结论仍走 `dy_research_record_write`，两者不混用。

## 费用内置 QA

费用模块读取[费用调研内置 QA、提取要素与附件结构](references/expense-research-guide.md)，按配置组提出汇总问题，再逐点收集并映射到费用矩阵。费用检查顺序面向用户显示为 `EXP-001`，完整子项显示为 `EXP-001-01`；记忆接口内部仍使用数字 `check_order` 与子项编号。附件页只提供字段结构和收集提示，模板示例、历史观察及“待确认”文本不构成项目事实。复用已确认事实，只追问最小缺口；明确确认后按下文范围、版本和待办流程写入记忆。

普通聊天调研中，来源解析出“待确认”“待补充”或“待业务签认”结论时，不能只生成候选台账后结束。有原生 `request_user_input` 能力时继续调用；宿主或当前模式未提供该能力时，明确说明并用文字提出同样的最小问题，不虚构工具、不为启用 QA 强制切换 Plan 模式。每组最多 3 个相互独立的问题，一题只解决一个缺口；公司/院区、业务范围、上线阶段或期间分别提问，不捆绑在同一题，也不推荐缺乏依据的单公司/多公司答案。优先复用来源与已答事实；不追问确认人或日期，`dy_research_record_write` 会自动记录当前 `FEISHU_CODEX_BOT_SENDER_USER_ID` 和系统时间。每次回答后核对剩余独立缺口：仍有可回答项就继续下一轮 QA，不以一轮已完成代替全批次；已明确暂缺、无权限或暂缓的项标为 `still_pending`，停止该项写入，不循环重复索要。此规则只适用于普通聊天调研任务；项目档案生成任务不自动接入 QA，仍按其独立生成流程执行。

对已解析来源，必须按覆盖台账分批处理待确认结论；不能只确认汇总问题、代表性样例或部分配置组后，就把剩余条目标成已完成。每个确认批次都要明确对应的业务回答、适用范围和依据；同一批次可由用户一次确认，不要求逐条单独确认。一轮 QA 最多处理 3 个相互独立的最小缺口；未完成批次不得报告完整导入、允许巡检使用或写入 `confirmed`。来源中的“候选，待业务签认”与“待确认”具有相同的批次确认要求；确认人 ID 与写入时间由 MCP 自动记录，不作为业务确认依据。

## 总账内置 QA

总账模块使用本 Skill 内置的 QA 流程，不要求用户先提供一轮完整答案。检查键使用当前矩阵中的 `GL-*` 编号；按配置项提出汇总问题，再依据参考指引拆分提取要素、收集所需材料。详细问题、字段和缺口映射见[总账调研参考](references/general-ledger-research-guide.md)。不得只问“需要吗”而丢掉范围、条件及附件要求。

## 调研记忆存储度与补问分流

顺序固定为：识别模块并读取指南 → 有附件先完整解析并提取已填答案/范围/缺口 → 用 `dy_module_memory_read` 分页查询当前模块记忆 → 调用 `dy_research_progress(trace_id, module, scope 或 scope_id)` → 只对来源与记忆都未解决的缺口提问或分流。无附件跳过解析。记忆只能通过工具读取，不能直接选择原始 Markdown 中的一份结论。即使用户尚未给出范围，也先只传模块调用；工具返回 `needs_scope` 时，再复用附件、会话及记忆中的范围线索，只有仍无法确定时才按指南询问一次。费用优先使用 `EXP-002 公司` 汇总问题；总账优先使用 `GL-1-002 核算主体范围` 汇总问题。只追问回答中仍缺失的公司/院区、业务范围、上线阶段或期间；项目名称不是存储度计算前置条件，不得为等项目名称而延迟分流。用户回答后立即用已明确的范围再次调用进度工具，再按结果分流；不得重复询问已经回答的范围字段，也不得另发一条内容相同的通用确认。

存储度是当前模块指南映射子项中，在同一适用范围内状态为 `confirmed` 且 `research_complete=true` 的已存储子项数除以指南子项总数；`retired`、部分事实和完整性未知记录不计作已回答。工具的 `unmapped_records` 与 `completeness_unknown` 必须向用户报告，不能将旧键静默丢弃、自动迁移或默认完整；核实映射与剩余要素后仍须业务确认及保存授权才能修订。费用按指南映射的 92 个子项计算；总账按指南映射的 82 个子项计算，未映射的 `GL-5-017` 补充问题不是额外记忆子项。

- 小于 70%：向用户说明已回答数、总数和百分比。有已填附件时，先处理来源答案、待签认与范围冲突，不因存储度低而重复要求空清单；来源解析和候选答案不计入已存储数。没有可复用的已填材料、仍需批量收集时，说明将生成固定模板，并调用 `dy_research_unanswered_export`。导出会创建工作区文件，必须先取得用户对导出的明确确认；模板固定为 `.dy_superpowers/research/<module>/unanswered-questions.xlsx`，已有文件不覆盖。把文件路径和未回答项数返回用户。
- 大于或等于 70%：不导出 Excel。按对应模块指南和检查顺序，对未回答子项分批调用原生 `request_user_input` 提问；每轮最多处理 3 个相互独立的最小缺口，由用户一次确认该批次，并在下一轮读取/复算后继续。已确认且 `scope_id` 未变的子项不重问；达到恰好 70% 时走互动问答。
- 进度工具返回 `needs_scope` 时，先按上述模块指南范围问题单次询问；范围不明时不计算、不导出，不能把不同公司、院区、业务或期间合并。文本范围对应多个稳定 `scope_id` 时，按已回答内容只追问区分范围所需字段。范围变化后重新读取并计算。
- 导出 Excel 仅用于整理未回答问题，不会将答案写入记忆。用户填写后仍须按批次业务确认流程核对并写入；只有调用方明确确认后才可生成该文件。达到 70% 后互动答案也须遵循批次确认、记忆写入及回读规则。

存储度只决定输出载体，不改变来源状态门槛、附件核对、业务确认、范围隔离、巡检边界或项目档案流程；调研 Skill 不主动触发巡检 Skill。

## QA、要素与附件归一化

问答能力按当前宿主实际提供的工具选择：原生 `request_user_input` 可用则使用；飞书 exec 提供 `feishu_qa` 服务的 `ask_feishu_user` 时使用该工具；飞书异步提问由宿主接收并续接答案。两者均不可用才文字降级，不能因没有原生表单而绕过可用的飞书 QA。异步发问后只处理不依赖该答案的独立工作，答案返回前不保存、不验收、不发布依赖结论。档案生成没有 QA handler，报告缺口而不尝试调用聊天 QA。

每个配置项先提出一个汇总问题。用户回答后，按模块指引“提取要素与附件关联”表拆成独立子项，检查键以当前矩阵为准，源表行次序不能自动作为子项编号；复用当前会话已经明确的信息，只追问缺少的公司/账套/业务/期间、例外和依据。确认人 ID 与写入时间由 MCP 自动记录。跨轮次维护待补充子项，不重问已回答且范围未变的内容。未提供的问题答案不能从示例行、附件观察、系统现状或邻近检查项推断。

两个模块共用同一整理顺序：按检查顺序找到模块内置 QA → 按关联表的子项提取要素 → 找到实际附件字段表 → 对照矩阵验收标准核对缺口 → 确认后按检查键与范围写入并回读。关联表统一记录模块、检查顺序、子项、提取指引要素、关联附件清单和记忆要求；来源审计定位保留在仓库本地 docs，不作为插件运行输入。附件字段保留原名、顺序、必填标记与数据范围；名称不同按表中显式别名解析，不能只靠相似名称匹配。数量汇总不能替代规则明细；无模板列为待收集，源 QA 无矩阵键则暂停该部分按键写入并报告，不并入相邻键。

一条回答仅覆盖子项部分要素时，只整理实际确认的事实与范围；经授权且满足必填字段后可保存这部分事实，不扩大为完整词库、全部规则或同组其他子项。未答要素留在待补问题中，该键仍不得作为已完成调研或已具备完整验收依据返回。参考指引的来源坐标用于理解规约，`evidence_ref` 必须指向本项目真实会话或已解析附件，不能冒用参考工作簿坐标充当本项目证据。

如果提取指引要求附件，按 QA 清单中对应模板逐字段收集，形成“应提供模板 → 已提供文件 → 已解析字段/行数 → 缺失字段/无法读取项”的核对表。附件按来源解析流程完整读取，保存于当前工作区 `.dy_superpowers-parsed/`；在模块记忆中只保存回答确认过的业务结论和脱敏来源定位。人员、银行账号及生产明细不写入记忆、trace 或 Wiki。没有附件时，逐项询问缺失内容；回答“暂缺/待确认”就保留待办，不得用空白替代“不适用”。

项目 Wiki 页面由用户确认的调研结论和经确认的模块主题笔记构建，并带有已登记来源文件的资料索引；不得发布附件全文、模板示例、待确认候选结论或解析档案。总账模块的页面按项目首页、模块目录、检查键主题页组织；主题页回链检查编号、子项、范围、来源文件名和工作表/单元格定位。用户未明确要求写入 Wiki 时，构建预览后须另行取得外发确认；用户已明确要求写入时，按下文授权继续。

把项目调研发布为面向业务人员的 Wiki 是三步受控流程，发布输入为按检查键的已确认调研记忆和已确认且绑定模块的主题笔记：

1. `dy_project_configure(trace_id, name, code, confirmed=true)`：经用户确认绑定当前工作区唯一的正式项目名称与稳定代号（小写字母数字连字符）。项目名称不确定时，先从调研材料整理候选名称请用户选定，不能从账套名、文件名或范围文本猜测；未配置或旧配置未经确认时构建与同步都会拒绝。项目一旦绑定不能改名或换代号。
2. `dy_wiki_build(trace_id, confirmed=true)`：按当前项目调研记忆在本地构建中文 Wiki 并生成发布清单（脚本入口 `scripts/build_research_wiki.py <工作区> --stage`）。页面固定为"知识库内项目首页 → 模块目录 → 业务主题"三级：项目首页含模块导航与已登记原始调研文件链接；模块目录按检查顺序列业务主题；主题页按子项展示结论、适用范围、来源和状态，不输出 YAML 元数据。"授权导入"的记录如实显示"来源记录，业务签认待核实"。构建后调研记录再发生变化时清单失效，须重新构建。原始调研文件登记在 `.dy_superpowers/sources.json`（名称 + 无凭据 HTTP(S) 链接，按项目绑定），按项目保存到 Git 仓库并在项目首页链接；巡检报告等交付物不入库。
3. `dy_wiki_sync(trace_id, confirmed=true)`：本次获得明确外发授权后，把已构建清单发布到 GitLab Wiki（REST，只增改不删页）。需设置 `DY_WIKI_API_URL`、`DY_WIKI_TOKEN`（只放环境变量，绝不写入文件或记忆），目标项目三选一：`DY_WIKI_PROJECT_ID` 现有项目；或首次同步 `DY_WIKI_GROUP_ID`+`DY_WIKI_PROJECT_NAME` 自动搜索/创建并持久化到工作区 wiki-target.json。同步前逐页校验所有权标记和上次同步哈希，多项目共享同一知识库时自动维护共享首页的项目目录与阅读指引；远端页 slug 由标题派生，因此页面键使用"代号-项目标识-业务键"的稳定前缀。无所有权标记的页面、被远端手工修改的页面和旧版首页都会拒绝覆盖，须按迁移方案单独处理；同步状态绑定实例、目标项目与本地项目，更换须显式重新配置。缺少授权、绑定、有效清单或凭据均拒绝发布；失败停止依赖发布的步骤。逐页已成功状态保留，可核对后重试；令牌不回显，不伪称已发布。

用户明确要求写入 Wiki 时，本次明确要求写入 Wiki 即作为外发确认；该指令同时作为保存确认，不重复询问是否保存，也不在 `dy_wiki_sync` 前重复询问外发确认。仍须取得覆盖批次的业务确认；同一批次可一次确认，不要求逐条单独确认；这项授权不代表候选结论已获业务确认，也不替代正式项目名称与稳定代号的绑定确认。确认结论写入记忆并回读成功后必须继续完成 Wiki 链路，不能停在候选台账、本地预览或“可以继续”的说明：缺少项目名称或稳定代号时先通过 QA 请用户补齐并确认；然后按顺序调用 `dy_project_configure`、`dy_wiki_build`，展示构建清单后调用 `dy_wiki_sync`。按业务确认与保存授权、项目绑定、记忆回读、清单新鲜度、凭据及目标配置、远端同步分层检查，任一步失败即停止其依赖步骤并报告具体阻塞；不相关调研可继续。不通过 QA 收集密钥，也不伪称发布成功。

清单字段按以下方式使用：

- `模块 + 检查顺序 + 调研子项编号 + 适用范围` 是完整回链维度；同一配置项可有多个独立调研子项。
- 在空白调研清单中，`调研结论` 是待收集和确认的项目事实；“回答参考”、示例及“待确认”文本都不是事实。在用户明确指定为调研结果的来源材料中，逐项识别已填写的实际结果、观察发现、明确决定和仍待确认事项；不要把整份结果都误判成模板，也不要将“待确认”转换为已确认事实。
- `适用条件与不适用边界` 用于确认本期范围和例外，不能只问是否需要。
- `建议材料 / 验证依据` 用于请求可追溯的来源；没有证据时标为待补充。
- 巡检矩阵的 `验收标准（调研后）` 用来判断当前结论是否足以驱动巡检；不充分时标出缺口并继续补问。来源中的配置观察值只证明文件记录了该观察，不能替代实时验证。

调研记录的回链维度：

- 模块、检查顺序或配置项；
- 调研子项编号；
- 配置路径和适用范围（公司、会计类型、业务、期间）。

检查顺序和子项编号必须原样取自当前模块矩阵或源清单；若两者冲突，暂停该键并查明映射，不能自行改号。每条记录至少保留模块、检查顺序、子项编号、结论、适用范围、来源或验证依据和确认状态。调用 `dy_research_record_write` 时，MCP 自动把当前 `FEISHU_CODEX_BOT_SENDER_USER_ID` 写入 `confirmed_by`，把系统当前时间写入 `confirmed_at`；调用方不询问或提供这两个字段。它们只表示本次记录操作者和写入时间，不证明附件中原业务确认人或历史确认日期。

## 完整调研结果导入

用户要求记忆已有结果时，先盘点文件结构并建立“来源调研结论 → 检查顺序 → 调研子项 → 记忆记录”的覆盖清单。默认“完整调研结果”指所有已填写的调研结论、范围、例外、不适用理由及待确认项，不自动指每条支撑结论的原始系统记录；同时统计原始明细行数及是否逐行入库。若用户明确要求所有明细逐条记忆，先验证当前工具是否支持；不支持时不能用归纳代替后称完整。不要只读取首个工作表、第一页、可见区域或标题摘要。逐项映射，不因内容相似而合并不同检查键；写入后按检查键回读并核对总数、缺项、状态和来源引用。

盘点每个工作表/页面/幻灯片的可见状态。默认纳入可见且与本次调研相关的内容；隐藏页、隐藏行列、历史归档和模板区单独计数并列明。用户要求包含或隐藏内容明显构成本次有效结果时才纳入，不能悄悄忽略或一概导入。

**来源状态是写入门槛。** 当前 `dy_research_record_write` 只接受 `confirmed=true`，落盘状态只有 `confirmed` 或 `retired`。分别核对三个门槛：来源回答、业务确认、保存授权。QA 表单已填写的 A 先作为来源回答；独立答题 Codex、附件解析器或无业务批准权限者只能转述证据，不能签认。空白 A、未回答项、附件里的单纯配置观察仍不算已确认。候选内容与范围展示后，由有权业务方按批次确认；另有保存授权才可写入。导入授权本身不构成业务确认；MCP 自动记录的发送人 ID 和系统时间仅为本次记录审计字段，也不代替业务确认。附件仅作业务回答的证据回链，不得将附件内容自行扩展成额外业务决定。写入仍须映射到当前矩阵键并通过回读验收；完整要素及所需附件齐备才传 `research_complete=true`，部分事实传 `false`，不明确时不宣称完整。

单条调研记忆必须符合 `dy_research_record_write` 的字段限制（结论最多 2000 字符，范围最多 500 字符，字段不得含换行），并映射到当前矩阵已有检查键。先保留结论所需的完整业务含义，再压缩冗余措辞。不得因为字段或检查键限制静默丢弃关键细节、改写成泛化摘要，或声称完成无法存入的部分；无法无损表达或没有检查键时，报告来源位置并阻塞该部分，等待记忆结构扩展或用户确认映射方案。禁止自行编造检查键。

只有当用户将范围限定为“调研结论”时，才可把明细表归纳为结论所需的数量、差异、异常、例外和证据位置，并同时报告原始明细行数与覆盖范围。不要把原始业务明细、员工个人信息、账号或凭据写入记忆。若用户要求保留全部明细，现有单条结论工具和矩阵键可能无法实现；将未逐行入库部分标为受阻，来源引用或摘要不等于明细已记忆。

## 多轮流程

1. 按检查键和适用范围调用 `dy_module_memory_read`，从返回的 `records` 中复用仍有效且已确认的结论。工具报告可见内容与内部数据不一致时，暂停使用该记录，核对原确认依据，再经用户确认通过 `dy_research_record_write(repair=true)` 和错误信息中的 `expected_revision` 修复；工具保留损坏块历史，其他独立子项可继续。不能绕过工具直接采用文件中的某一份结论。
2. 如果使用源材料，先按源文件解析流程完成清单和覆盖核对；再按模块调研清单逐项提问或将已填写的来源结果整理为候选结论。一次只处理当前最小缺口。信息不足时标记为 `待补充`，不要猜测。
3. 将回答整理为候选结论，区分事实、业务决定、材料依据和待确认内容；必要时继续追问范围、例外、边界和生效期间。
4. QA 表单中已填写的 A 按来源回答处理；整理时保留原意、范围和附件回链，再核实回答者权限和批次业务确认。若 A 为空、未回答或仅有附件观察，则列为待补充，不推断答案。用户授权导入文件只授权处理文件，不会把空白或未确认内容变成业务确认。
5. 候选结论整理完成后，必须向用户展示候选内容、适用范围、依据和剩余缺口，并按批次取得业务确认。用户本次明确要求写入 Wiki 时，无须重复询问是否保存；但该授权不能代替业务确认。其他情形须明确询问是否确认保存。没有对应确认时，只保留会话中的候选结论或待办，不得调用 `dy_research_record_write`，不得传入 `confirmed=true`，不得声称已写入记忆。
6. 只对用户明确确认且符合当前记忆工具状态语义的结论调用 `dy_research_record_write`；来源未确认、未映射或超长项保留在覆盖台账并报告为受阻。已有记录先读取，沿用 `scope_id` 并传入最新 `expected_revision=revision`。冲突时重新读取、核对差异并再次请求确认，不能盲目重试。保留旧版本，不覆盖其他范围或历史。写入后通过 `dy_module_memory_read` 按检查键及 `scope_id` 回读，并核对覆盖清单；同一键存在多个范围时明确范围，不得选用其他公司的结论；不要整文件覆盖模块调研记忆。
7. 返回发起方时，分别报告文件/页数、调研结论数、原始明细行数、可映射数、已写入并回读数、来源待确认数、未映射数、超长数、隐私排除数、解析失败数及阻塞键。只有约定范围内每个有效结论批次都获用户确认、可安全写入且成功回读、无待确认/未映射/失败项时，才可称该范围“完整导入”。若用户要求保存全部原始明细，还须证明明细逐条写入支持其存储的结构。业务验收与来源导入状态分开报告。

## 跨会话恢复

会话开始时，按需用 `dy_memory_read` 读取 `delivery-register.md` 中的调研待办，再按检查键读取已确认结论。结束或切换任务前，展示仍待补充的检查键、阻塞原因、下一条最小问题及原巡检项；用户确认保存待办后，读取现有 `delivery-register.md`，保留其他台账内容，用 `dy_memory_write` 更新对应待办，同时将刚读取的完整原文作为 `expected_content`。冲突时重新读取并合并，展示合并结果经确认后重试，不能覆盖其他会话的更新。只记录待办和问题，不保存未确认答案或候选结论；这类待办不能驱动验收。

恢复时先核对待办是否仍适用，并通过 `dy_module_memory_read` 读取最新确认记录；有冲突或范围变化时继续补问。确认结论保存成功后，更新对应待办为已解决也须遵循记忆写入确认规则。未获保存确认时，在回复中给出待办并说明跨会话需重新提供。

## 调研记录结构

每个 `模块 + 检查顺序 + 调研子项编号 + scope_id` 维护一条当前有效记录，历史轮次追加在记录的 `history` 中，不覆盖原答案。不同范围分别保存当前结论与历史；首次未指定 `scope_id` 时工具按规范化范围文本生成标识，后续沿用返回值；重命名显示范围也沿用该标识。新增范围不会自动废止其他范围；原范围失效时，逐检查键经确认使用 `status=retired`、`retirement_reason` 和当前 `expected_revision` 显式停用，再暂停依赖检查。落盘的基础检查键格式为 `module:check_order:research_id`（如 `expense:1:01`）。落盘记录包含：

```yaml
module: expense | general-ledger
check_order: "矩阵原始检查顺序：费用如 1，总账如 GL-1-001；不得自行改号"
research_id: "调研子项编号"
config_item: "配置项"
conclusion: "已确认结论"
scope: "公司/账套/业务/期间"
scope_id: "稳定范围标识"
evidence_ref: "材料或验证依据的脱敏引用"
status: confirmed | retired
confirmed_by: "确认人"
confirmed_at: "确认日期"
updated_at: "最近修订时间"
revision: "读取时返回的块版本；修订时作为 expected_revision 传入，不手工修改"
history: []
```

状态规则：`pending` 和 `needs_confirmation` 是会话过程状态，不落盘——`pending` 只能提出问题，`needs_confirmation` 只能展示整理结果并请求确认。`dy_research_record_write` 仅接受经确认的结论修订、停用或修复，同一适用范围的新结论修订旧结论时，旧记录移入 `history` 并标记为 `superseded`，保留替代关系；只有 `confirmed` 的记录才能被巡检使用。当前最小待确认问题和对应“验收标准（调研后）”不写入记录，通过检查键回链巡检矩阵获取。若用户一次回答包含多个子项，仍按子项拆分并分别确认，不得用一段回答覆盖不同范围。

## 与巡检衔接

巡检发现调研结论缺失、过期、冲突或不能支撑“验收标准（调研后）”时，暂停依赖该结论的子项并调用本 skill。补充调研确认后，回到原 `检查顺序 + 调研子项编号`，按对应验收标准继续，不把补问当作巡检通过。

补充调研请求必须携带：原 `trace_id`、`check_key`、阻塞原因、对应验收标准、已知事实和一个最小问题。返回 `confirmed / still_pending` 两组键：这里的 `confirmed` 只包含同范围记忆已回读且足以支撑对应验收标准的键；只保存局部确认事实、附件字段仍缺失或验收口径未齐的键列入 `still_pending`，同时说明已保存事实和剩余缺口。该返回分组不新增落盘状态，也不等同于记忆记录的 `status`。巡检只恢复前一组，其他键保持阻塞并进入报告。

## 记忆和追踪约束

- 记忆只属于当前工作区，一个工作区对应一个项目；不得读取或写入其他工作区。
- 不写入密码、令牌、员工个人信息或生产业务明细；敏感内容留在授权系统。
- 同一多轮任务的 MCP 调用沿用 `trace_id`。工具自动记录允许的记忆/调研正文、搜索词及脱敏查询条件；密码、令牌、常见个人字段值和 Odoo 返回行不进入追踪。不要手工将未确认问答写入 trace。
- `dy_research_record_write` 必须获得用户明确确认；工具校验通过不等于获得写入授权。已确认记录的当前内容由工具自动追踪。
- 在关联记忆或证据读取调用中，附带可选 `trace_context`：`skill`、`module`、`check_order`、`research_id`，已有确认记录再附带读取到的 `scope_id`、`revision`。只填已知标识，不能编造缺失范围或版本；详见[运行边界](../../docs/runtime-boundaries.md#链路与业务标签)。

## 输出

输出中文调研台账和待办：已确认结论、依据、适用范围、确认状态、待补充问题，以及可供巡检继续使用的检查键。不要把模板示例或未确认回答写成项目事实。

调研结论较多时，不要把大量长结论放入单张宽表。先用短摘要列来源、解析完整性、结论总数、确认状态数量和当前阻塞；再单独列公司/院区、业务范围、上线阶段或期间等待补信息；先展示待确认与待业务签认项，之后再列已确认项。按配置组分节，每条结论逐条使用短标签换行展示“子项、候选结论、适用范围、业务确认状态、记录操作人/写入时间、来源依据”；同组状态一致时可合并状态说明，但不能合并或删减结论内容。过长的来源明细另列为附件或索引，不重复铺开到正文。
