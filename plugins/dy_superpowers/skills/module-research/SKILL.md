# 模块调研

## 目标

通过多轮问答和核对调研材料，形成按项目、模块、检查项和适用范围组织的可追溯事实。用户要求导入已有调研结果时，任务是完整提取来源中的有效调研结论并按检查键记忆；不能把该要求降为只保存摘要或几个示例。记忆状态表示来源内容已经导入，不自动表示业务负责人重新确认、配置验收通过或巡检通过。

## 调研来源

先确认模块、公司/院区、业务范围、上线阶段和期间等基础上下文，再读取对应模块清单及用户提供的源材料。费用模块读取 `../expense-inspection/references/inspection-matrix.md`，总账读取 `../general-ledger-inspection/references/inspection-matrix.md`；其他模块使用其对应清单。处理 Excel、其他 Office 文件、PDF 或图片时，遵循[源文件解析与完整性核对](references/source-intake.md)，并使用当前 Codex 环境可用的对应文件解析能力。

清单字段按以下方式使用：

- `模块 + 检查顺序 + 调研子项编号 + 适用范围` 是完整回链维度；同一配置项可有多个独立调研子项。
- 在空白调研清单中，`调研结论` 是待收集和确认的项目事实；“回答参考”、示例及“待确认”文本都不是事实。在用户明确指定为调研结果的来源材料中，逐项识别已填写的实际结果、观察发现、明确决定和仍待确认事项；不要把整份结果都误判成模板，也不要将“待确认”转换为已确认事实。
- `适用条件与不适用边界` 用于确认本期范围和例外，不能只问是否需要。
- `建议材料 / 验证依据` 用于请求可追溯的来源；没有证据时标为待补充。
- 巡检矩阵的 `验收标准（调研后）` 用来判断当前结论是否足以驱动巡检；不充分时标出缺口并继续补问。来源中的配置观察值只证明文件记录了该观察，不能替代实时验证。

调研记录的回链维度：

- 模块、检查顺序或配置项；
- 调研子项编号；
- 配置路径和适用范围（公司、会计类型、业务、期间）。

检查顺序和子项编号必须原样取自当前模块矩阵或源清单；若两者冲突，暂停该键并查明映射，不能自行改号。每条记录至少保留模块、检查顺序、子项编号、结论、适用范围、来源或验证依据、确认状态和日期。源文件未提供确认人时如实标记“未提供”，不得把导入授权人填成业务确认人。工具要求的字段只填事实；确有必填字段缺失时明确说明，不能伪造。

## 完整调研结果导入

用户要求记忆已有结果时，先盘点文件结构并建立“来源调研结论 → 检查顺序 → 调研子项 → 记忆记录”的覆盖清单。默认“完整调研结果”指所有已填写的调研结论、范围、例外、不适用理由及待确认项，不自动指每条支撑结论的原始系统记录；同时统计原始明细行数及是否逐行入库。若用户明确要求所有明细逐条记忆，先验证当前工具是否支持；不支持时不能用归纳代替后称完整。不要只读取首个工作表、第一页、可见区域或标题摘要。逐项映射，不因内容相似而合并不同检查键；写入后按检查键回读并核对总数、缺项、状态和来源引用。

盘点每个工作表/页面/幻灯片的可见状态。默认纳入可见且与本次调研相关的内容；隐藏页、隐藏行列、历史归档和模板区单独计数并列明。用户要求包含或隐藏内容明显构成本次有效结果时才纳入，不能悄悄忽略或一概导入。

**来源状态是写入门槛。** 当前 `dy_research_record_write` 只接受 `confirmed=true`，落盘状态只有 `confirmed` 或 `retired`；`confirmed` 会被巡检当作可用结论。只有来源明确记载业务确认且确认人/日期可追溯时，才能将来源结论写成 `confirmed`。用户授权“导入/记忆文件”本身不是业务确认，工具的 `confirmed` 参数也不能当作纯粹的“允许保存”标志。对来源中的配置观察、仅待业务确认的结果或缺少确认人/日期的结论，若当前对话尚未取得业务确认，就不得调用该工具伪标为 `confirmed`；将其列为受阻来源项，报告当前工具缺少不驱动巡检的来源记录状态，等待此能力或业务确认。阻塞项必须明列，不能声称全部导入。

单条调研记忆必须符合 `dy_research_record_write` 的字段限制（结论最多 2000 字符，范围最多 500 字符，字段不得含换行），并映射到当前矩阵已有检查键。先保留结论所需的完整业务含义，再压缩冗余措辞。不得因为字段或检查键限制静默丢弃关键细节、改写成泛化摘要，或声称完成无法存入的部分；无法无损表达或没有检查键时，报告来源位置并阻塞该部分，等待记忆结构扩展或用户确认映射方案。禁止自行编造检查键。

只有当用户将范围限定为“调研结论”时，才可把明细表归纳为结论所需的数量、差异、异常、例外和证据位置，并同时报告原始明细行数与覆盖范围。不要把原始业务明细、员工个人信息、账号或凭据写入记忆。若用户要求保留全部明细，现有单条结论工具和矩阵键可能无法实现；将未逐行入库部分标为受阻，来源引用或摘要不等于明细已记忆。

## 多轮流程

1. 按检查键和适用范围调用 `dy_module_memory_read`，从返回的 `records` 中复用仍有效且已确认的结论。工具报告可见内容与内部数据不一致时，暂停使用该记录，核对原确认依据，再经用户确认通过 `dy_research_record_write(repair=true)` 和错误信息中的 `expected_revision` 修复；工具保留损坏块历史，其他独立子项可继续。不能绕过工具直接采用文件中的某一份结论。
2. 如果使用源材料，先按源文件解析流程完成清单和覆盖核对；再按模块调研清单逐项提问或将已填写的来源结果整理为候选结论。一次只处理当前最小缺口。信息不足时标记为 `待补充`，不要猜测。
3. 将回答整理为候选结论，区分事实、业务决定、材料依据和待确认内容；必要时继续追问范围、例外、边界和生效期间。
4. 向确认人展示本轮整理结果，明确要求确认或修订。未确认的互动回答不得驱动巡检，也不得写成已确认事实。用户授权导入文件代表可处理和保存，不等于来源未确认内容已获业务确认。
5. 只对符合当前记忆工具状态语义的结论调用 `dy_research_record_write`；来源未确认、未映射或超长项保留在覆盖台账并报告为受阻，不得用 `confirmed=true` 绕过。已有记录先读取，沿用 `scope_id` 并传入最新 `expected_revision=revision`。冲突时重新读取、核对差异并再次确认，不能盲目重试。保留旧版本，不覆盖其他范围或历史。写入后通过 `dy_module_memory_read` 按检查键及 `scope_id` 回读，并核对覆盖清单；同一键存在多个范围时明确范围，不得选用其他公司的结论；不要整文件覆盖模块调研记忆。
6. 返回发起方时，分别报告文件/页数、调研结论数、原始明细行数、可映射数、已写入并回读数、来源待确认数、未映射数、超长数、隐私排除数、解析失败数及阻塞键。只有约定范围内每条有效结论都可安全写入且成功回读、无待确认/未映射/失败项时，才可称该范围“完整导入”。若用户要求保存全部原始明细，还须证明明细逐条写入支持其存储的结构。业务验收与来源导入状态分开报告。

## 跨会话恢复

会话开始时，按需用 `dy_memory_read` 读取 `delivery-register.md` 中的调研待办，再按检查键读取已确认结论。结束或切换任务前，展示仍待补充的检查键、阻塞原因、下一条最小问题及原巡检项；用户确认保存待办后，读取现有 `delivery-register.md`，保留其他台账内容，用 `dy_memory_write` 更新对应待办，同时将刚读取的完整原文作为 `expected_content`。冲突时重新读取并合并，展示合并结果经确认后重试，不能覆盖其他会话的更新。只记录待办和问题，不保存未确认答案或候选结论；这类待办不能驱动验收。

恢复时先核对待办是否仍适用，并通过 `dy_module_memory_read` 读取最新确认记录；有冲突或范围变化时继续补问。确认结论保存成功后，更新对应待办为已解决也须遵循记忆写入确认规则。未获保存确认时，在回复中给出待办并说明跨会话需重新提供。

## 调研记录结构

每个 `模块 + 检查顺序 + 调研子项编号 + scope_id` 维护一条当前有效记录，历史轮次追加在记录的 `history` 中，不覆盖原答案。不同范围分别保存当前结论与历史；首次未指定 `scope_id` 时工具按规范化范围文本生成标识，后续沿用返回值；重命名显示范围也沿用该标识。新增范围不会自动废止其他范围；原范围失效时，逐检查键经确认使用 `status=retired`、`retirement_reason` 和当前 `expected_revision` 显式停用，再暂停依赖检查。落盘的基础检查键格式为 `module:check_order:research_id`（如 `expense:1:01`）。落盘记录包含：

```yaml
module: expense | general-ledger
check_order: "矩阵原始检查顺序：费用如 1，总账如 EXP-1-001；不得自行改号"
research_id: "调研子项编号"
config_item: "配置项"
conclusion: "已确认结论"
scope: "公司/账套/业务/期间"
scope_id: "稳定范围标识"
evidence_ref: "材料或验证依据的脱敏引用"
status: confirmed | retired
confirmed_by: "确认人"
confirmed_at: "确认日期"
updated_at: "最近修订时间"
revision: "读取时返回的块版本；修订时作为 expected_revision 传入，不手工修改"
history: []
```

状态规则：`pending` 和 `needs_confirmation` 是会话过程状态，不落盘——`pending` 只能提出问题，`needs_confirmation` 只能展示整理结果并请求确认。`dy_research_record_write` 仅接受经确认的结论修订、停用或修复，同一适用范围的新结论修订旧结论时，旧记录移入 `history` 并标记为 `superseded`，保留替代关系；只有 `confirmed` 的记录才能被巡检使用。当前最小待确认问题和对应“验收标准（调研后）”不写入记录，通过检查键回链巡检矩阵获取。若用户一次回答包含多个子项，仍按子项拆分并分别确认，不得用一段回答覆盖不同范围。

## 与巡检衔接

巡检发现调研结论缺失、过期、冲突或不能支撑“验收标准（调研后）”时，暂停依赖该结论的子项并调用本 skill。补充调研确认后，回到原 `检查顺序 + 调研子项编号`，按对应验收标准继续，不把补问当作巡检通过。

补充调研请求必须携带：原 `trace_id`、`check_key`、阻塞原因、对应验收标准、已知事实和一个最小问题。调研完成后返回 `confirmed / still_pending` 两组键；巡检只恢复 `confirmed` 键，其他键保持阻塞并进入报告。

## 记忆和追踪约束

- 记忆只属于当前工作区，一个工作区对应一个项目；不得读取或写入其他工作区。
- 不写入密码、令牌、员工个人信息或生产业务明细；敏感内容留在授权系统。
- 同一多轮任务的 MCP 调用沿用 `trace_id`。工具自动记录允许的记忆/调研正文、搜索词及脱敏查询条件；密码、令牌、常见个人字段值和 Odoo 返回行不进入追踪。不要手工将未确认问答写入 trace。
- `dy_research_record_write` 必须获得用户明确确认；工具校验通过不等于获得写入授权。已确认记录的当前内容由工具自动追踪。
- 在关联记忆或证据读取调用中，附带可选 `trace_context`：`skill`、`module`、`check_order`、`research_id`，已有确认记录再附带读取到的 `scope_id`、`revision`。只填已知标识，不能编造缺失范围或版本；详见[运行边界](../../docs/runtime-boundaries.md#链路与业务标签)。

## 输出

输出中文调研台账和待办：已确认结论、依据、适用范围、确认状态、待补充问题，以及可供巡检继续使用的检查键。不要把模板示例或未确认回答写成项目事实。
