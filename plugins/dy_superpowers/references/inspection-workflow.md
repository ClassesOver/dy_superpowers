# 巡检通用流程

以当前范围最新确认的答卷及关联附件为业务依据，利用现有知识定位规则，再通过只读工具检索当前系统取证，逐项判断是否对齐。不使用静态巡检矩阵；调研问题投影仅供问答，未确认的填写内容不能替代当前确认答卷。巡检独立运行：缺少答卷依据时只在报告中标记缺口，不在巡检内补问、导入或保存答案。

公共规则：[答卷读取](common/qa-answer-read.md)、[知识检索](common/knowledge-retrieval.md)、[Odoo 只读查询](common/odoo-readonly-query.md)。报告遵循[校验合同](../docs/inspection-validation.md)，证据关联见[来源核对](inspection-source-validation.md)。

## 简洁流程

按“最新答卷 → 环境连接 → 提取要求 → 知识检索 → 系统查询 → 对齐比较”执行。公司或日期缺失只阻塞依赖分支，独立检查继续。

1. **读取最新答卷。** 按答卷读取规则调用 dy_module_memory_read（默认新版 QA），取得当前模块、业务范围的最新确认答案、附件字段明细、答案版本及同步答卷路径。无确认答案、局部答案、缺附件或附件摘要漂移的问题保留待确认/未检查，独立问题继续。
2. **使用环境连接。** 按只读查询规则先调用 dy_odoo_environment_info 核对配置是否可用；dy_inspection_prepare 可省略 environment 自动复用。不打印连接配置或凭据，不向用户重复索要连接。公司及业务日期从答卷复用，仅补实际依赖的缺口。
3. **提取对齐要求。** 调用 dy_inspection_prepare(module, scope_id, environment)，原样保留 basis 及全部 expected_checks，分母取自 expected_checks。逐题把确认答案、附件 requirements 整理为“业务要求、适用范围、预期系统值或行为”；返回的 detail_checks 逐项保留 text 与 source_ref，字段可合并查询但不得省略，未核验填待确认或未检查。每项明确核验目标 verification_target：configuration 为系统配置、business 为业务效果、document 为制度或材料本身；类型未明确不作通过结论。附件 source_refs 保留当前确认绑定的 reference 和 sha256；摘要不一致时该项标待确认，不能沿用旧证据。
4. **检索知识并查系统。** 按知识检索规则理解相关模块、模型和规则，结合领域 source-queries 将业务要求映射为模块、模型、字段、关联、权限及计算规则；再按只读查询规则核对安装模块、真实字段和当前记录，按答卷预期值逐项查询比较。知识解释规则，当前系统查询证明现状；知识未命中、读取不完整、源码与部署版本不符时保留限制，不能推断不存在或通过。
5. **比较并报告。** 逐项比较预期与实值，记录差异、真实证据和未验证边界；不能仅核对记录数量或名称。先 dy_inspection_validate，展示当前模板全部问题的覆盖、门禁与边界，再按下方模板回复。用户确认保存后才 dy_inspection_report_save(confirmed=true)，再 dy_inspection_report_read；需要业务 PDF 时，对已保存报告调用 dy_inspection_report_export_pdf，已有 PDF 不覆盖。

## 取证规则

source-queries 仅技术查询配方，不定义业务要求。巡检只用只读工具，不调用任何配置写入、导入或模块变更工具，巡检请求不授权修配置或写业务数据。业务效果不能由配置存在替代：公司隔离、岗位、金额日期边界、预算、凭证、支付制证须对应业务效果证据，配置存在不能证明操作成功；支付、制证、关账等仅查既有结果或签认材料，不执行操作来验证，无法验证时保留材料/人工缺口。

系统配置项必须取得当前 Odoo 证据；材料项须独立核验文件并填写 observed_at，晚于答案确认且不晚于 verified_at。调研附件是预期依据，不能复制改名作为独立核验证据，不能自证对齐。业务效果另需真实结果材料或签认。在题级 reason 中按各要求写清“预期→实值→比较结论”，列明公司/期间范围及分页是否查全；检索成功、空结果或结构校验通过都不等于业务对齐。新增模块/模型/字段发现工具可辅助定位，差异候选工具空结果不证明无差异。

当前答案 revision、附件摘要、全部 requirements 与真实证据逐项记录，包括待确认题的全部已确认附件要求及明细；未核验项可无证据。trace_context 复用 basis（含服务生成的 connection_fingerprint），补 question_id、answer_revision 及必要的 requirement_id；Odoo 证据须本工作区成功 tool.end 与对应 odoo.read 同时存在。连接安全指纹由服务生成，不填写或显示地址、账号及凭据。要求级证据匹配 requirement_id，题级汇总可引用本题实际要求 ID。跨范围、模块或连接不能放行。校验器验证覆盖与证据关联，业务语义、公司/期间选择及查询完整性仍须模型逐项复核。

## 结论与版本

按校验合同保留全部问题及已确认附件要求。对齐对应通过，有确凿差异对应不通过或部分通过；缺业务依据标待确认，未取得系统证据标未检查，不适用须有完整确认答案和真实依据。未知项不能删除凑通过。模板、答案版本、附件或连接变化时重新 prepare，不沿用旧巡检结论；旧报告仅供历史 read，不能用新验证放行，也不能冒称补导 PDF 通过。

## 固定回复

```text
巡检模块：{模块名称}
业务范围：{公司或阶段}
巡检依据：当前最新确认答卷及关联附件
核对结果：{已对齐数量、存在差异数量、待确认或未检查数量}
差异与待补：{业务要求／系统现状／差异或缺口／证据概述；无则填“无”}
下一步：{补充材料或建议处理；无则省略}
报告：{实际已保存报告链接；尚未保存则说明}
```

内部标识、版本哈希、查询参数、模型技术名及连接信息仅用于工具和证据关联，不在用户回复中展开。来源审计不写 Skill 或业务记忆；内部校验合同仍须完整填写。
