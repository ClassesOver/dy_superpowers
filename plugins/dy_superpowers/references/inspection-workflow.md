# 巡检通用执行流程

费用、总账及后续领域巡检共用本流程。领域入口负责模块标识、检查清单、业务重点和源码查询；报告字段和门禁以 [巡检校验合同](../docs/inspection-validation.md) 为准。

## 1. 建立本次范围

确认当前工作区的单一项目、目标环境/数据库、Odoo 修订及定制模块、公司/账套、业务日期/期间、岗位与交付批次。未知项如实列出；环境或公司不清楚时阻塞依赖它们的记录查询，独立检查可继续。凭据只由运行环境提供。

读取领域清单，逐一建立 `module + check_order + research_id + scope_id + environment` 对应的检查记录。原始检查顺序和子项编号保持稳定，配置项名称只作展示。每个子项有自己的调研要求、适用条件和完整验收标准；父项结果从子项汇总，不能反向复制。表格、问答和文件只是输入载体，解析细节见 [来源驱动巡检](inspection-source-validation.md)。

每次 MCP 调用带同一 `trace_id`；按子项读取记忆、调研或 Odoo 时，携带已知 `trace_context`：`skill`、`module`、`check_order`、`research_id`、`environment`。读到确认调研后再原样加入 `scope_id`、`revision`。不得编造标识、版本或证据事件；断点恢复时重新核对范围和版本，详见 [运行边界](../docs/runtime-boundaries.md)。

## 2. 关联调研并处理缺口

使用 `dy_module_memory_read` 按检查键和稳定 `scope_id` 读取，核对返回 `records` 中记录的键、范围、状态、确认人/日期和来源；整模块读取满页时继续分页。只使用当前 `confirmed` 记录驱动验收，模板、示例、导入授权、旧配置观察和 Knowledge 检索均不能替代业务确认。

结论缺失、停用、冲突、范围不明或不能支撑验收标准时，暂停依赖子项并调用 `module-research`，传入原 `trace_id`、检查键、阻塞原因、完整验收标准、已知事实及一个最小问题。允许跨多轮补充；确认后由 `dy_research_record_write` 保存，修订带最新 `expected_revision`，随后按同键和 `scope_id` 回读。只恢复已确认且范围匹配的子项，其余继续待确认。

依据确认结论判定适用、不适用或后期范围。不适用只豁免对应子项，须有确认依据；后期制度义务还须说明本期衔接。不得为绕过缺口把待确认改成不适用。

## 3. 建立只读证据链

依 P0、P1、P2 处理，按领域查询参考定位配置：

1. `dy_odoo_module_list_installed` / `dy_odoo_module_info` 核对安装状态与版本；安装是数据库级事实，不等于目标公司已启用或已验收。模块列表每页最多 100 条，满页继续 offset，取全后才能下未安装结论。
2. `dy_odoo_model_fields` 核对字段类型、关联、存储和可搜索性，再使用 `dy_odoo_record_search` / `dy_odoo_record_read` 读取最小必要字段。字段存在不能证明归属语义；按源码和实际元数据确认公司/结构、共享记录、父子范围、日期与状态。版本不符或真实范围字段缺失时停止该配方，不能退回无界限查询。
3. 所有汇总和全量判断必须逐页取全，核对重复 ID、offset 和上限。分页重复、读取失败或达到上限则标记不完整。需要含归档核验时显式传 `kwargs.context={"active_test":false}` 并保留范围条件；只支持布尔型 `active_test`，不能借 context 扩大公司权限。
4. 区分来源时点观察、当前库配置和目标业务日期推算。计算字段若按今天生效，不得作为目标日期的独立启用开关；当前库筛选不构成历史快照。空结果、权限不足、连接失败和范围不清楚都不能直接判缺陷。数量差异先核对环境、权限、归档和父子口径。

源码与 `dy_knowledge_module_info` / `dy_knowledge_search` 只提供模型和业务线索，不证明实际账套配置。来源含外部验收标准时，对照当前领域标准，冲突阻塞对应分支，不静默选版本；保留来源位置、摘要哈希和映射差异。

## 4. 核验业务效果并形成结论

每项按确认调研选择验收分支，记录验证方法、操作者/岗位、环境、带时区的时间、最小证据引用及限制。配置快照只能证明所读配置；权限隔离、流程、防重、金额边界、支付、制证、关账等效果须有真实岗位的正例、边界例、反例及业务签认，不能用管理员单一成功或模板存在替代。

Odoo 工具仅用于受限只读查询。需要修改配置、安装模块、执行审批/支付/结转/凭证操作的分支，记录缺口和验证计划，转人工或另行授权的流程；本巡检不执行这些业务方法。连接或权限错误不盲目重试，也不切换管理员或扩大访问范围。中断时保留已读覆盖和待办，恢复后重新核对版本与完整性。

逐子项使用 `通过/部分通过/不通过/不适用/待确认/未检查/未知` 并说明依据；区分配置缺陷、账务结果差异、制度决策、材料缺口与外部开发。明确失败不得因其他项未查而从报告消失。问题附影响、下一步和复查条件；责任人/完成日期缺失时标待指定。

## 5. 校验、展示和保存

按 [巡检校验合同](../docs/inspection-validation.md) 构造报告：范围内每个子项进入 `expected_checks` 并恰有一条当前 `records`；其余进入 `excluded_checks` 并写明调研缺口、需操作验证或本轮未安排等理由。两类合计覆盖当前矩阵全部键；完整范围内未完成项仍须有待确认/未检查记录。部分范围门禁只代表纳入项，展示 N/M 覆盖度及未验证部分，不能称整模块交付通过。

结果保留完整验收标准、当前矩阵原始文件 SHA-256、调研 `revision/scope_id` 和验证时间。Odoo 证据必须回链同一工作区、同模型、同检查键/范围/环境/调研版本的成功调用。先调用 `dy_inspection_validate`；`valid=false` 修正记录，`valid=true` 后仍须读 `gate/coverage/limitations`。校验只验证结构、版本和引用对应关系，不证明业务证据真实，也不授予执行权限。

向用户展示结论、覆盖、阻塞、下一步及校验限制。获得保存确认后使用 `dy_inspection_report_save(confirmed=true)`，由工具重新校验并生成报告编号；用响应中的模块与编号调用 `dy_inspection_report_read` 回读。文件保存在 `.dy_superpowers/reports/<module>/<YYYY-MM-DD>/`，含业务 PDF 和保留完整检查数据的 Markdown；旧报告不覆盖。历史 Markdown 补 PDF 使用 `dy_inspection_report_export_pdf`，须通过当前校验。

当前正式校验、门禁和报告工具仅支持 `expense`、`general-ledger`。其他模块可使用合法模块标识保存确认调研，但尚无本模块矩阵键校验和正式报告闭环；新建 skill 目录不会自动增加这些能力，具体见创建器的 [编写合同](../skills/inspection-skill-creator/references/authoring-contract.md)。

## 6. 留痕与复查

项目事实只保存在当前工作区 `.dy_superpowers/`；调研修订使用调研工具，普通交付待办经确认使用 `dy_memory_write` 并传最近读取的 `expected_content`，冲突时重读合并。参考清单不写入项目事实。工具自动追踪允许的记忆/调研正文、搜索词及脱敏 domain；不记录密码、令牌、常见个人字段值、未确认问答或 Odoo 返回行，不另建遥测通道。

结束时列出完成覆盖、阻塞检查键、证据限制与下一步。跨会话恢复及交付前，重新读取当前调研并校验矩阵/范围/环境；变化后旧结果仅作历史，相关项重新验证。不得只替换哈希或版本号延续通过；既有报告不会自动失效重写。交付关联规则见 [交付领域](../docs/delivery-domain.md)。
