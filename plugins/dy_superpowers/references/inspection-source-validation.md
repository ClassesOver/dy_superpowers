# 来源驱动巡检与端到端验证

供费用、总账巡检使用；不改变 module-research 的采集或写入契约。已有调研可以是问答、Excel、Word、PDF、接口结果等，文件布局不是巡检输入合同。

## 把已有调研作为巡检输入

1. 建立候选检查清单：保留来源文件名、内容摘要 SHA-256、工作表/页/单元格、原检查编号、子项、要求、例外、依据与适用范围；不把格式转换当作业务确认。
2. 合并父项只继承配置项、编号等结构字段，结论逐子项配对。公式结论应核对引用目标与缓存；不能只读 data_only 后把无缓存当空白，也不能执行未知公式。外部工作簿自带的“结果”只是旧结论，不复制为本次通过。
3. 来源编号与当前矩阵建立双向映射。例如费用清单可能用 DY-01，而矩阵用 1；只有配置项语义和子项都一致时才映射，并保留原号。总账可能用 EXP-1-001，不因 EXP 前缀把它误归入费用。矩阵外子项、重复/冲突结论和未映射项单独列明；不能删掉或随意改号。
4. 同时读结论主表与关联明细的范围、例外、待确认说明。主表写“已配置”而明细写“需确认”时，只能说明当前资料有该观察，不足以完成对应业务判断。原始员工、银行账号等敏感明细不复制到报告或 trace。
5. 分清四种语义：“需要安装/需存在”是要求；“已安装/已有 N 条”是来源时点观察；“不需要/不适用”是带范围的决定；“需确认”是未定条件。一句中可并存多种语义，不把整行粗分为已通过或不适用。未提供业务确认人、日期或公司时不虚构。
6. 若来源自带验收标准，与插件矩阵逐项比较并记录差异。报告里的 acceptance_standard 和 matrix_revision 仍取当前插件矩阵；外部标准差异是受影响检查分支的阻塞，不能为了 valid=true 私改标准或覆盖插件矩阵。当前校验器不会自动判断附件标准冲突，报告须明示。

## 按调研覆盖挑选检查项（部分范围巡检）

调研驱动的巡检不要求一次覆盖全部矩阵子项，按下列规则挑选：

1. **纳入标准**：只把"调研结论已覆盖 且 本轮可验证"的子项放入 `expected_checks`——即可用只读配置核验，或本轮已安排操作验证的子项。每个纳入项必须有一条当前结果记录。
2. **其余子项全部进 `excluded_checks` 并写分类理由**：调研缺口（来源待确认/未映射）、需操作验证（岗位/页面/支付/关账/流程样例）、本轮未安排。excluded 项不生成记录，但必须枚举不漏——漏项仍会被校验拒绝，这是防止静默跳过的底线。
3. **部分范围门禁只代表纳入项**：校验结果会标注"部分范围巡检 N/M"，报告一页结论自动带覆盖度说明；不得把部分范围报告表述为整模块通过。后续轮次把 excluded 项逐步转入 expected；最终整体验收仍需全矩阵覆盖。
4. **不虚构占位记录**：调研结论未经业务确认时，纳入项结果保持"待确认"，部分范围巡检因此不会产出"通过"——这是正确结果。为凑门禁把未检查项写成通过、或为省记录漏报 excluded，都违反本规则。
5. 挑选结果写入报告的 `evidence_summary`（"从来源 N 个子项中挑选 M 个"），便于评审判断本轮覆盖面。

## 先做可比性检查，再判断配置差异

- 先核对环境/数据库身份（脱敏引用）、模块版本、公司/账套、来源核查时点、业务日期和账号允许范围。账号只见一家公司的记录，不能和多公司汇总直接判断缺失。不能擅自切管理员、sudo 或扩大允许公司来追平数量。
- 用 dy_odoo_model_fields 核对输出字段以及 domain 字段。区分 company_id、company_ids 和没有公司字段的共享配置；Many2many 范围为空不能自行解释为全公司共享或全公司不可用。需结合源码 record rule、页面入口及实际授权账户核实。
- search_read 每页最多100条。所有需要数量/金额总计的模型都分页至不足一页，记录 offset、筛选口径和唯一 ID；达到预设上限、分页重复或读取失败时标记不完整，不以已读前缀下结论。未传 active_test 上下文时受 Odoo 默认 active 过滤影响，不能把结果称为含归档配置的全库记录。
- 数量相符只说明当前筛选口径的快照相符。数量不同先列“待核实差异”：来源范围不同、账号可见性、归档过滤、数据变更、父子记录口径都可能导致差异；在范围确认、证据充分后才判断真实配置缺陷。
- 日期按确认的业务日期判断：启用标志为真但已过期不算当前有效；后期规则、申请规则和报销规则分别核对。来源明确“不启用/不续期”的历史规则，不能为追平历史数量建议重新启用；该排除不自动豁免其他仍适用功能。as_of 只用于筛选当前库的业务日期，不是历史数据库快照。
- 先选政策头、公司/项目和适用日期，再通过真实父字段查明细。不能把多个费用政策混算，也不能用关系条数冒充城市/政策数量。原始明细数、有效明细数、淡旺季关联数分别报告。

## 结果与证据

已确认且可独立验证的子项继续检查，不因其他子项待确认而全部停止。要求只读能证明什么、还缺什么要写清：页面可见性、岗位隔离、金额边界、支付回单、核销闭环、重复制证、开关账顺序等不能只凭配置记录存在判通过。需要写操作验证的分支转人工或另行授权，不调用任意业务方法。

Odoo 调用附带已知 trace_context；只有已有真实确认记录时，才带该记录返回的 scope_id/revision，不为了通过校验编造。明确结果的 evidence_refs 必须回链到本次成功、同模型、同检查子项、同范围和同版本的完整调用；同父项下一个模型的读事件不自动证明其他子项。来源未确认时可保存带来源回链和只读诊断的“待确认”报告，不写虚假的 confirmed 调研。

报告同时列出来源覆盖、矩阵覆盖、可自动核验的配方覆盖、实际查询结果和业务未验证范围。矩阵全部172个子项有状态，不等于172个子项全部验收；协议测试、来源解析、配置诊断与业务验收分别下结论。

## 可重复测试

- 默认测试使用模拟 Odoo 与真实 stdio MCP，覆盖模块翻页、确认门槛、同范围版本证据、缺项/伪造证据拒绝、修订失效、报告生成与回读。
- live 测试需显式提供 `DY_E2E_ODOO_ENV_FILE`；来源驱动测试另提供 `DY_E2E_RESEARCH_SOURCES`（费用/总账候选 JSON）与 `DY_E2E_SOURCE_FILE_EXPENSE` / `DY_E2E_SOURCE_FILE_LEDGER` 原文件路径供哈希核验，通过 `DY_E2E_AS_OF` 指定业务日期。默认未指定公司 ID 时只核对字段；`DY_E2E_VISIBLE_SCOPE_DIAGNOSTIC=1` 显式启用当前账号可见公司范围的配置诊断，仍不代表附件公司范围已确认。来源数量只有在范围及环境显式确认后才做正式比较。来源文件和连接配置只留本地，不提交到仓库。
- live 测试只读 Odoo；报告写到隔离临时工作区。没有完整业务签认时门禁保持待确认，即使技术测试成功也不能报告项目验收通过。
