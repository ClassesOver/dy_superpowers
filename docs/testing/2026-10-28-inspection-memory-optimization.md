# 面向巡检的记忆读取与准备视图优化验证

## 范围与边界

本轮实现用户批准的记忆优化，并将巡检前准备、局部补问恢复和依赖变化复查纳入设计。不更换 Markdown 事实源，不迁移正式业务记忆，不修改业务系统，不自动提交、推送或替换正式安装。工作树保留上一轮附件解析与 QA 卡点修复。

## 实现

1. 明确验收结果必须以当前同范围、未停用且显式 `research_complete=true` 的调研为前提。旧记录缺少完整性标记不再默认完整；待确认、未知、未检查仍可表达缺口。没有批量修改旧业务记录。
2. `dy_module_memory_read` 增加 `current/summary/full` 视图，省略保持旧调用的完整返回；`checks` 支持至多100个检查键，并与单键参数互斥。先按范围与检查键筛选和分页，再展开所选页历史。精简视图不展开历史文件，进度异常清单只保留摘要。模块文件仍需扫描、解析和校验，未宣称新增数据库索引。
3. 新增只读 `dy_inspection_prepare`，按当前矩阵与指定 `scope_id/environment` 列出调研准备状态、完整验收标准、补问入口及复查原因。上次记录按完整检查键匹配；其他范围或环境不复用。补齐一个子项仅解除该子项阻塞。
4. 分开呈现调研存储度、所选矩阵项的调研就绪数量和上次结果声明计数；`verification.performed=false`，始终 `evidence_reusable=false`。不拉起 QA、不执行 Odoo 查询、不选择验收分支、不延续历史通过，也不改写报告。`next_question` 是指南入口，仍须结合已有事实拆分为一次一题。
5. 准备事件使用既有 trace 字段保存项数、就绪数和阻塞数，不扩大正文留痕范围。`expected_count/count/result_count` 分别对应上述三项计数。

## 失败基线与修复

- 最初定向测试复现了全模块历史先展开、精简视图仍展开历史、批量检查键未过滤、进度异常返回完整正文、旧记录被默认完整的问题，再实施最小修复。
- 畸形上次记录中的列表、对象或数字可使处理器产生内部错误；新增5种参数回归后改为明确拒绝非法参数。
- 准备视图的计数和环境字段最初被 trace 白名单过滤；新增行为回归观察到 `KeyError: expected_count` 后，改用既有计数字段与 `trace_context`。没有放宽脱敏规则。
- 独立审查发现新准备接口接受中文或带空格环境，但后续证据 trace 要求稳定机器标识。新增3类回归先观察到2 failed、1 passed，再统一新接口 schema 与函数校验；未改宽既有证据 trace 契约。测试追踪目录统一隔离到临时 `CODEX_HOME`。
- 首次全量运行：578 passed、4 skipped、2 failed、355 warnings，455.11秒。两项失败均为费用/总账跨范围成功场景的既有虚构夹具缺少完整性标记；仅为该成功夹具显式增加 `research_complete=true`，不放宽生产门槛。该矩阵回归随后4 passed。

## 使用限制

旧记录须在实际补问和用户确认后按当前版本修订，不能仅补一个标记冒充调研完成。准备就绪不等于验收通过；范围、期间、环境的业务变化仍须明确确认，不能从自由文本自动推断。

本轮未跑真实 Odoo 业务巡检或再次发起模型调研 QA；4项真实 Odoo 测试需要显式环境/来源条件，不把跳过算作业务通过。官方隔离安装成功也不等于所有宿主、网络或模型会话都稳定。正式安装暂未替换，提交操作另行记录，尚未推送。
